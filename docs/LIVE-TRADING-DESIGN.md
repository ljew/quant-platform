# 日频实盘系统方案 v0.1

> 2026-10-28 · 基于对 `quant-platform` dev@e5103c9 的实测核查
> 目标：把 fresh_ma 组合从「回测结论」推进到「能持续验证的实盘 sleeve」

---

## 0. 结论先说

三句话：

1. **策略够格进验证，但系统不够格。** 从「信号」到「订单」这条链，平台上**一次都没跑通过**（证据见 §1）。当前缺的不是策略，是 L3-L6 这段工程。
2. **合规上，个人不能做外接自动下单。** 平台必须定位为「决策支持系统 + 人工执行」，全自动只有一条路：策略移植进券商终端（PTrade / QMT）内跑。这不是选择题，是红线。
3. **日频的真正优势不是「简单」，是「一天只有一次决策 + 16 小时纠错窗口」。** 方案围绕这个优势设计：收盘后算、次日开盘执行、白天可以发现问题并人工叫停。

### 1.1 两个必须指出的隐患

**(a) 当日 K 线的时点可疑。** `data_scheduler` 配的是 19:00 跑（`RUN_HOUR=19`，`_DATA_READY_HOUR=16`），但实际 `kline_daily` 里 10-26/27/28 三天的 `created_at` 都是**当天 08:00**——早于 A 股开盘。要么是补跑逻辑写错了日期，要么数据源返回了未收盘的占位数据。

> 无论哪种，结论一样：**`trade_date == today` 不能作为「数据就绪」的判据**。实盘必须用 §4.6 的完整性校验。这是实盘系统的第一条铁律：宁可空跑，不可错跑。

**(b) fresh_ma 的选股排序是字典序，不是信号强度。** `portfolio_fresh.py:278` 是 `cands.sort()`，排序键为 `(0 if high_tight_flag else 1, symbol)`。日均候选 158 个、只取 20 个，**等于「按股票代码取前 20 只」**。回测数字是用同一套规则算的所以自洽，但这意味着「top20」缺乏经济含义，且对股票代码增删敏感。上实盘前必须换成确定性打分（见 §4.7）。

## 2. 三个要先纠正的认知

### 2.1 「能跑回测」≠「能跑实盘」

回测引擎把**意图**和**成交**合并在一次推演里：

```
信号 → 假设 100% 成交于次日开盘价 → 持仓 → 净值
```

实盘必须拆成两段，中间隔着一个「现实」：

```
信号 → 目标持仓 → 订单意图 → 风控 → 实际下单 → 部分成交/未成交/被拒 → 实际持仓 → 对账 → 净值
```

差别不是精度问题，是**状态归属**问题：回测的持仓是模型变量，实盘的持仓是券商回报。混用会让「未成交」这种日常事件变成账本错乱。

### 2.2 「日频简单」的真相

简单的部分：一天一次决策，不用管 tick、不用管盘中波动、不用低延迟。

难的部分（全部是日频特有）：
- **未成交**：一字涨停买不进、停牌、流动性不足 → 目标组合与实际持仓永久偏离，需要「次日重试」机制
- **除权除息**：持仓跨除权日，成本价和止损基准会失真 → 必须用后复权维护，券商回报用原价，两套换算
- **集合竞价**：想按开盘价成交，必须 09:25 前挂单；09:30 后挂就是另一个价格
- **满仓无缓冲**：20 只 × 5% = 100%，实际成交价比信号价高一点就资金不足

### 2.3 「实盘验证」要分两个目标

| 目标 | 验证什么 | 需要多久 | 判据 |
|---|---|---|---|
| **工程验证** | 管道每天按时出单、订单可执行、对账平 | 约 1 个月（20 个交易日） | 成交率 > 90%，对账差异 = 0 |
| **策略验证** | edge 是否还在 | 6-12 个月（至少一个 regime 周期） | 实盘超额 vs 影子组合超额偏离 < 2pp |

fresh_ma 的诚实披露是：全 250 天 +12.95%，但**无门控时回撤 -29.7%**、**主动段只有 102 天**、7 月 regime 切换时门控滞后 6 周才重开。这个样本量支撑不了「策略有效」的结论，只能支撑「值得花 1 个月验证工程，再花半年观察 edge」。

## 3. 目标架构

```
┌─ L1 数据 ──────────────────────────────────────────────┐
│ kline_daily / adj_factor_daily / index_membership      │  已有
│ ↓ 完整性闸门（§4.6）                                    │
├─ L2 信号 ──────────────────────────────────────────────┤
│ signal_actions (action/streak/resonance/ma20/quality)   │  已有，需恢复每日跑
│ ↓                                                      │
├─ L3 组合意图 ──────────────────────────────────────────┤
│ target_portfolio = f(信号, 实际持仓, 门控, 日历)         │  ★新建
│   纯函数、无副作用、可重算                               │
│ ↓                                                      │
├─ L4 订单意图 ──────────────────────────────────────────┤
│ order_intent = target − actual（逐票 diff）             │  ★新建
│   幂等键 (trade_date, symbol, side)                     │
│ ↓                                                      │
├─ L5 风控闸门 ──────────────────────────────────────────┤
│ 单笔 5 项 + 组合 6 项 + 熔断 2 项                        │  ★重写（现 risk.py 是桩）
│ ↓                                                      │
├─ L6 执行 ──────────────────────────────────────────────┤
│ 人工（Phase 3） / PTrade 内跑（Phase 4，可选）           │  ★新建
│ ↓                                                      │
├─ L7 对账归因 ──────────────────────────────────────────┤
│ fills / positions / 滑点分布 / 影子组合偏离 / 归因       │  ★新建
└────────────────────────────────────────────────────────┘
```

### 核心原则（三条，全部服务「可复现」）

1. **单一事实源 = 券商回报。** 实际持仓只从成交回报来，不从模型推。规则基于实际持仓算目标，天然处理「未成交→次日重试」。
2. **规则是纯函数。** `target = rule(signals, actual_positions, gate_state, calendar)`，同样输入必得同样输出。这样重跑无害，回测与实盘同源。
3. **决策快照不可变。** 每天生成订单时，把「当时的 enabled 策略集、卡片档位、门控状态、候选池」存一份快照。否则事后无法回答「那天为什么买这只」。

第 3 条针对的是现存的隐性风险：`portfolio_fresh.py:133` 每天用 `resolve_strategy_quality(db)` 现算 `enabled` 集合。卡片档位一变，同一个历史日期重算出的候选池就变了——回测结论无法复现。

## 4. 六个设计决策

### 4.1 执行通道：合规红线先画死

依据 2026-08-28 施行的中证协+中基协《证券公司交易信息系统接入管理规范（试行）》（中证协发〔2026〕181号）：

| 做法 | 判定 | 结论 |
|---|---|---|
| 平台调券商 API 下单 | 客户系统生成指令 → 属「接入」 | ❌ 第六条白名单不含自然人 |
| 写 CSV/Redis/共享内存给 QMT 读 | 原文「电子文件**等**载体」 | ❌ 第三十二条同样不含 |
| 读终端内存/UI 自动化点按钮 | 外挂（反采） | ❌ 本轮清理核心 |
| 策略代码跑在 PTrade/QMT **内** | 指令由券商终端生成 | ✅ 允许，**须报备** |
| 平台出清单，人在 APP 手工下单 | 平台只是展示数据 | ✅ 无需报备 |

**判定口诀：不看载体，看指令是谁生成的。**

所以 Phase 3 的「实盘」= 平台出订单清单 → 微信推送 → 人工在券商 APP 下单 → 收盘后导入成交对账。零合规风险，且能立刻拿到最重要的数据：**真实滑点与成交率**。

全自动（Phase 4）唯一路径是策略移植进 PTrade：日频、20 只、调仓集中，PTrade 的云端托管比 QMT 更合适（不用 24 小时开机）。但要重写代码 + 报备 + 三层验证，是另一笔工程账，且**不建议在工程验证通过前启动**。

### 4.2 单一账本 + 目标持仓纯函数

不搞「策略账本 + 券商账本」双账本（容易出幽灵持仓）。只维护一份实际持仓：

```
live_position  ← 唯一事实源（来自成交回报）
target         ← rule(信号, live_position, gate, 日历)
orders         ← target − live_position
```

未成交的处理是**自动的**：某只票今天该买 1000 股只成交 600，`live_position` 就是 600；次日规则再算 target 仍是 1000，diff 出 400 再买。不需要额外的重试逻辑。

代价：持仓的 `entry_date` / `peak`（止损基准）必须自己维护在 `live_position` 里，从首次成交日记起。

### 4.3 双组合并行：实盘 + 影子

每交易日同时跑两条线：

| 线 | 用什么数据 | 用途 |
|---|---|---|
| **实盘 sleeve** | 真实成交回报 | 真实净值、真实滑点 |
| **影子组合** | 假设 100% 按开盘价成交（复用 `run_portfolio_fresh` 的重演逻辑，增量版） | 对照基准 |

**两条线的净值差异就是执行成本**。差异突然扩大 = 执行出问题（滑点变大、成交率下降、数据错）；差异长期稳定在成本量级 = 系统健康。

没有影子组合，「实盘验证」就只是看赚了还是亏了，无法区分是策略问题还是执行问题。

### 4.4 风控三层

现有 `core/broker/risk.py` 是桩：`_today_loss()` 硬编码返回 0.0；涨跌停用 ±10% 一刀切（没考虑 ST 5%、创业板/科创板 20%、北交所 30%）；资金检查按「券商订单表」算而非账户实际资金。**实盘不能用，需要重写**。

| 层 | 规则 | 违规动作 |
|---|---|---|
| **单笔** | 价格合理性（偏离昨收 ±X%）、数量整手、可用资金、可用持仓（T+1 卖出限制） | 拒单 |
| **组合** | 单票 ≤ 5%、持仓数 ≤ 20、单行业 ≤ 25%、现金 ≥ 3%、单日换手 ≤ 40% | 截断/拒单/告警 |
| **熔断** | 组合回撤 -15% 停新开仓；单日亏损 -3% 停止当日所有交易 | 全局暂停 |

熔断那条不是摆设：fresh_ma 无门控时回撤 -29.7%，实盘必须有硬刹车。

### 4.5 幂等与断点续跑

- 订单意图唯一键 `(trade_date, symbol, side)`，重复生成走 UPSERT 不新增
- 每个阶段落库，进程崩溃后从断点续，不重跑已完成的阶段
- 状态机：`DRAFT → APPROVED → SENT → FILLED / PARTIAL / REJECTED / EXPIRED`
- 同一交易日重复执行流水线 → 结果完全一致（这是纯函数设计换来的）

### 4.6 数据完整性闸门（硬约束）

出单前必须全部通过，任一失败 → **当日不出单，发告警**：

| 检查 | 阈值 |
|---|---|
| 当日 `kline_daily` 覆盖股票数 | ≥ 前一交易日的 98% |
| 全市场成交额 | 在近 20 日均值的 50%~200% 区间 |
| 当日 OHLC 合法性 | `high ≥ max(open,close) ≥ min(open,close) ≥ low`，无 0 值 |
| 复权因子 | 当日 `adj_factor_daily` 有更新 |
| 交易日历 | 当天是交易日，且不是半日市 |

这条直接针对 §1.1(a) 那个疑点。**数据可疑比没有数据更危险**。

### 4.7 上实盘前必须改的三处策略细节

这三处不改，实盘数字会和回测对不上：

| 问题 | 现状 | 改法 |
|---|---|---|
| 选股排序 | 字典序（`cands.sort()`） | 确定性打分：`high_tight_flag` > `resonance` > `streak` 小者优先 > symbol（保证可复现，且有经济含义） |
| 满仓无缓冲 | 20 × 5% = 100%，无现金 | 目标仓位改为 20 × 4.75%，留 5% 现金吸收成交价偏差 |
| 最小资金门槛 | 未校验 | 单只预算 ≥ 股价 × 100 × 2（否则高价股买不满 5%）。资金 40 万以下会出现系统性建仓缺口 |

第三条要展开说：单只 5%，总资金 40 万 → 单只 2 万 → 只能买 200 元以下的股票。A 股 100 元以上约 10-15%，20 只里可能碰到 2-3 只买不起。要么资金 ≥ 40 万，要么接受「高价股跳过」并在回测里同样处理（否则回测偏高）。

## 5. 数据模型（5 张新表，`live_` 前缀）

与研究数据物理隔离——实盘数据不可重算，不能被研究流水线覆盖。

```
live_position          实际持仓（唯一事实源）
  symbol PK, shares, avg_cost, entry_date, peak_close, last_update
  └ peak_close 用于移动止损，从首次成交日起逐日更新

live_order_intent      订单意图
  id, trade_date, symbol, side, target_shares, actual_shares, qty,
  limit_price, ref_price, reason, status, reject_reason, filled_qty,
  filled_price, snapshot_id, created_at
  UNIQUE(trade_date, symbol, side)

live_decision_snapshot 决策快照（不可变，可复现的锚点）
  id PK, trade_date, strategy_key, enabled_strategies_json, card_tiers_json,
  gate_open, gate_exc, gate_n, candidates_hash, params_json, created_at

live_fill              成交回报
  id, intent_id, trade_date, symbol, side, qty, price, amount,
  commission, stamp_tax, transfer_fee, source(manual/csv/broker), created_at

live_equity            每日净值
  trade_date PK, cash, market_value, total, n_positions,
  shadow_total, divergence_pct, created_at
```

`paper_*` 表保持不动（它们是模拟盘/研究用），`broker_orders` 可保留作历史，新链路不复用——避免两种语义混在一张表。

## 6. 日频时序

关键决策：**不必等 19:00 的 ETL**。fresh_ma 只需要日线收盘价 + 策略扫描结果，15:30 就能算，留出充足时间做风控和推送。

| 时点 | 动作 | 依赖 | 现状 |
|---|---|---|---|
| 15:00 | 收盘 | — | |
| 15:05 | 当日 K 线入库 + 完整性闸门 | 数据源 | ⚠️ 需修（当前 08:00 就写了当日数据，见 §1.1a） |
| 15:30 | 策略扫描（8 个策略）+ 信号判定 → `signal_actions` | 当日收盘 | ❌ 需恢复 |
| 15:45 | 门控判定（PIT）+ 目标组合 + 订单意图 | 上一步 | ★新建 |
| 16:00 | 风控闸门（三层） | 上一步 | ★新建 |
| 16:15 | 企微推送：订单清单 + 理由 + 门控状态 | 上一步 | ★新建 |
| 次日 09:15-09:25 | 人工挂单（集合竞价，限价 = 昨收 × 1.02 上限） | 人 | |
| 次日 09:35 | 录入成交（或对账单 CSV 导入） | 人 | ★新建 |
| 次日 15:30 | 对账：意图 vs 成交，更新 `live_position` / `live_equity` | 上一步 | ★新建 |
| 次日 16:00 | 偏离报告：实盘 vs 影子，滑点分布，告警 | 上一步 | ★新建 |

为什么挂单价用「昨收 × 1.02」而不是市价单：日频策略的 alpha 在 10 天量级，2% 的价格容忍度不会吃掉 edge，但能避免「开盘瞬间冲高成交在最高点」。

| 开跑 | 建议 40-50 万（满足 §4.7 最小资金门槛），单只约 2 万 |
| 每日对账 | 意图 vs 成交，滑点分布，成交率 |
| 每周复盘 | 实盘 vs 影子偏离分析 |

**验收**：20 个交易日，成交率 > 90%，滑点中位数 < 0.3%，对账差异 = 0，实盘与影子偏离 < 2pp。

### Phase 4 · 自动化通道（可选，视 Phase 3 结果）

PTrade 移植 + 报备 + 三层验证。**前提是 Phase 3 证明这套逻辑执行得动、成本可接受**。若人工每天 5 分钟能搞定 20 只，未必需要花这笔工程账。

### Phase 5 · 持续验证（长期）

影子偏离周报、regime 门控监控（门控关闭/开启时点告警）、归因（alpha vs beta）。

## 8. 风险清单

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | 合规：外接系统被清理 | 账户被限制交易 | Phase 3 纯人工执行，不碰任何券商接口 |
| 2 | 数据时点错误（§1.1a） | 信号建立在坏数据上 | §4.6 完整性闸门 + 每日推送数据健康度 |
| 3 | fresh_ma 的 edge 是 regime 依赖 | 切换期失效 | 影子组合监控 + 熔断 + 门控告警 |
| 4 | 样本量不足（主动段 102 天） | 无法判断策略是否真有效 | 明确区分工程验证/策略验证（§2.3） |
| 5 | 字典序选股 | 「top20」无经济含义 | §4.7 改打分 |
| 6 | 满仓无缓冲 | 资金不足，建仓不全 | 留 5% 现金 |
| 7 | 高价股买不起 | 系统性建仓缺口 | 资金门槛 ≥ 40 万 or 回测同步处理 |
| 8 | 分红除权 | 成本/止损基准失真 | 后复权维护 + 除权日校准 |
| 9 | 流水线静默失败 | 某天没出单但以为出了 | 三类告警 + `live_equity` 缺日检测 |
| 10 | 手工录入错误 | 账本污染 | 对账单 CSV 导入优先，手工补录需二次确认 |

## 9. 需要你拍板的四件事

1. **资金规模**：Phase 3 用多少？低于 40 万会出现高价股建仓缺口（§4.7）。
2. **执行方式**：先走「人工下单 + 对账」跑 20 天（推荐），还是直接奔 PTrade 移植？
3. **策略范围**：只上 fresh_ma 一个 sleeve，还是经典镜像组合并行跑对照？
4. **券商通道**：现在有没有 PTrade / QMT 权限？若没有，Phase 4 从计划里去掉，长期维持人工执行。
