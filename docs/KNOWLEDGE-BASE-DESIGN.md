# 量化投研知识库 · 设计方案

> 版本 v1.0（待老刘拍板）· 2026-10-26
> 范围：在 `quant-platform` 现有 Medallion 数据层之上，新增「知识层」（文档 → 事件 → 特征）
> 性质：本文档仅为设计，**未改动任何生产代码**；DDL 已在临时库验证可执行
> 配套：`docs/schema/knowledge_base_v1.sql`（12 张核心表，实测建表通过）

---

## 摘要：知识库的价值不在「存」，在「能不能产出不骗人的特征表」

你要的东西，一句话定义清楚：

> **任意一个交易日收盘后，能从行情 + 文本 + 事件，稳定产出一张 `(symbol, trade_date) → 特征向量` 的表；每个值都能回答三个问题：什么时候可得的、从哪算出来的、漏了多少。**

按这个定义，你现在缺的不是「一个知识库」。你已经有了 1.4GB 文本、三路数据源、声明式抽取管道、词典和 LLM 两个打分器。缺的是**中间那一段加工链**——文档没有身份、实体没有对齐、事件没有结构、特征没有元数据、时间没有 PIT。

这一段补上，知识库自然就成立了；补不上，再多的文本也只是躺在硬盘上的字节。

## 一、先看一个数字：1.4GB 文本 → 每天 14 只股票

实测你现有库里的真实状况：

| 项目 | 实测值 | 说明 |
|---|---|---|
| 原始文本量 | **1.44 GB** | news 1.3G + 公告 103M + 公众号 24M |
| 结构化后的个股情绪表 | 6,768 行 | `news_stock_daily` |
| 时间跨度 | 2020-02-28 → 2026-10-23 | 6.6 年 |
| **日均覆盖股票数** | **14.2 只** | 而同期 A 股约 5,500 只 |
| **截面覆盖率** | **约 0.26%** | 截面因子通常要求 ≥ 60% |
| 每条记录的字段数 | 5 个 | symbol/date/mentions/bull/bear/net |
| 因子注册表条目 | **1 条** | `factor_registry`，基本没启用 |

**结论：不是数据不够，是加工链断了。**

你手上的语料强度，做「市场级情绪」够用（824 天连续），做「个股截面因子」完全不够——每天只有 14 只票有信号，任何 IC 计算都是噪声。这也是为什么 `factor_registry` 里只有 1 条记录：文本因子压根没进入过候选池。

三个原因，都在代码里（见第六节）：实体链接用今天的股票名匹配历史的文本、情绪是累计值不是当日值、没有 PIT 时间列。

### 1.1 S1 已落地（2026-10-26）：真实数字比预估更极端

S1（文档层建表 + 存量回填）已执行完毕，实测结果：

| 项目 | 预估 | **实测** |
|---|---|---|
| 原始 parquet 行数 | — | **5,415,100 行** |
| 按 `article_id` 唯一 | 63,771 | 63,771 篇（重复率 **98.8%**） |
| 再按 `content_hash` 去重后主文档 | — | **31,278 篇**（再砍 51%） |
| 公告 | — | 20,619 篇，均长 **49 字** |
| 新闻 | — | 36,152 篇，均长 **139 字** |
| 公众号 | — | 7,000 篇，均长 **2,324 字** |
| 实体链接覆盖 | — | **20,565 / 20,619 篇公告（99.7%）**，涉及 4,074 个标的 |
| PIT 空值 | 0 | **0** ✅ |
| 全量回填耗时 | — | 95 秒（可重跑，两次结果完全一致） |

三条实测结论，修正了设计阶段的假设：

**① 三个源的信息密度完全不同**

- **公告只有标题**（均长 49 字，实为「分类|标题」），没有正文
- **新闻是摘要流**（均长 139 字，p90 仅 187），不是全文
- **只有公众号有全文**（均长 2,324 字）

所以「LLM 抽取全文」这个前提不成立。公告的价值在**标题里的事件类型**（增持/回购/立案/中标），规则抽取比 LLM 更准更快；LLM 应该只用来处理标题歧义的边界情况。

**② raw 层有两个采集缺陷（比 schema 设计重要得多）**

- **东财新闻抽取器分页重复**：`em_202609043865136348_4`、`_5`、`_6`… 同一篇稿子在同一批次的不同分页被重复记录，`article_id` 只差页码后缀
- **公众号重复抓取**：单篇被 wewe-rss 重复抓 45 次（同一账号同一文章）

这两个在抽取层修掉，raw 体积能砍 98%。S1 的 `content_hash` 能兜住，但应该在源头解决。

**③ 语料时间跨度根本不够做因子验证（当前最大阻塞）**

| 覆盖档位 | 天数 | 区间 |
|---|---|---|
| ≥200 篇/日 | 38 天 | 2026-06-22 → 2026-10-26 |
| ≥50 篇/日 | 84 天 | 2026-02-24 → 2026-10-22 |
| **公告 ∩ 新闻 共同交易日** | **33 天** | **2026-08-31 → 2026-10-26** |

33 个交易日算 IC 没有任何统计意义（经验门槛：至少 250 个交易日、覆盖一轮完整涨跌）。公众号虽有 2020 年起的记录，但 7,000 篇散落在少数日期，不连续。

**这意味着 S2 之前必须插入 S1.5：历史语料回补。**否则整条链路建完也只够跑通、不够验证。

## 二、三条硬约束（先定，决定后面所有表长什么样）

**约束 1：一文档一 `doc_id`，append-only**
`doc_id = sha1(source || source_doc_id)`，同时存 `content_hash = sha1(title + body)`。
理由：转载去重、增量幂等、事件溯源，全靠这两个哈希。你现在去重只用了 `article_id`（源内唯一），跨源同一篇稿子会重复计入情绪——转载 10 次就把情绪放大 10 倍。

**约束 2：一切数值必须带 `available_at`**
不是 `published_at`，是**「我最早能拿它做决策的时刻」**。
A 股公告 80% 在盘后 15:00–24:00 发布。用自然日归到当日截面 = 用收盘后才知道的信息做当天决策，IC 会虚高到不可信。这一列是数据质量的分水岭。

**约束 3：特征长表存、宽表算**
`feat_value(feature_id, entity_id, trade_date, value)` 长表入库，需要宽表时 DuckDB `PIVOT` 即时生成。
理由：你现在的 `factor_daily` 是 14 列宽表，加第 15 个因子要 `ALTER TABLE` + 改模型 + 改前端。知识库的特征会有 200+ 个，宽表方案必然崩。

## 三、五层结构

| 层 | 职责 | 关键产出 | 现有对应物 |
|---|---|---|---|
| **L1 文档层** | 原文归档、去重、PIT 定级 | `doc_document` / `doc_chunk` | 现有 parquet（无统一 ID） |
| **L2 语义层** | 实体链接 + 事件抽取 + 关系 | `doc_entity` / `ev_event` / `ent_relation` | 仅"简称子串匹配"，无事件 |
| **L3 特征层** | 特征的注册、计算、落值 | `feat_registry` / `feat_value` / `label_*` | `factor_daily` 宽表 + 5 字段情绪 |
| **L4 应用层** | 数据集快照、质量门禁 | `ds_snapshot` / `qa_check` | `pipeline_runs`（仅运行日志） |
| **L0 源** | 抽取 | 各源 parquet | `sources.yaml` ✅ 已很成熟 |

**设计取向：L0 不动，L1 新建，L2 是重点，L3 替换现有情绪表，L4 补门禁。**

行情侧（`kline_daily` 988 万行、`adj_factor_daily` 1001 万行）已经很好，不碰。它在本方案里只作为「特征计算的原料」和「标签计算的基准」。

## 四、表设计要点

完整 DDL 见 `docs/schema/knowledge_base_v1.sql`（已在 SQLite 实测建表：19 张表 + FTS5 索引 + 29 条事件类型种子）。

只讲四个决定成败的设计选择：

### 4.1 `doc_document.trade_date_applicable` —— 一列解决前视

```
交易日 15:00:00 及之前发布  → T
交易日 15:00:00 之后发布    → 下一交易日
非交易日发布                → 下一交易日
```

存量文档回填一次即可，之后每篇新文档在 ingest 时算定。所有下游聚合只按这一列 group by，**不允许任何地方直接用 `published_at::date`**。

> **实测踩到的坑（值得单独记住）**：第一版实现用 `hour*60 + minute` 判断是否在 15:00 前，丢掉了秒。
> 结果 812 条 **15:00:18–15:00:46 发布的「收盘播报」**被误判为「15:00 前」，归进了当日截面——占全库 1.3%。
> 这就是典型的前视泄漏：用 15:00 之后才发出的信息，去解释 15:00 收盘时的截面。
> 修法是把判断精确到秒（`hour*3600 + minute*60 + second <= 15*3600`），并把该检查固化进 `qa_check`。
> **没有 PIT 自洽性校验的话，这 812 条永远不会被发现**，只会表现为某个文本因子 IC 莫名其妙偏高。

### 4.2 `doc_entity.match_type` + `confidence` —— 实体链接要能审计

不只存「这篇文档关联了 sh600519」，还要存：
- 怎么匹配上的（`source_code` / `exact_alias` / `full_name` / `code` / `fuzzy`）
- 置信度（0~1）
- **证据片段 `evidence` + 字符偏移 `span_start/span_end`**

> **实体 ID 格式必须沿用 `sh600519` / `sz300750` 前缀式**，与 `kline_daily`、`factor_daily`、`stocks`、`index_kline_daily` 一致。若另起 `.SH` 后缀式，之后每张表 join 都要做一次映射，且漏做时表现为「静默零匹配」——最难查的一类 bug。

理由：误配是文本因子最大的隐性杀手。有了 evidence，出问题时能一条 SQL 拉出来人工复核；没有，你永远不知道 IC 为什么不对。

### 4.3 `ev_event.span_text` —— 事件必须可追溯

每个事件都存「原文哪句话支撑这个判断」。这是 LLM 抽取能不能信的前提，也是你以后回头看「这个因子为什么有效」的唯一线索。

同时 `payload_json` 存事件专属字段（减持比例、预告净利区间、诉讼金额），避免为每类事件建一张表。

### 4.4 `feat_registry.compute_sql` —— 口径固化在库里

每个特征把计算方法以 SQL 存在注册表。好处：
- 重算不用翻代码，一条 `SELECT` 就能重建
- 换口径时改 `version` 而不是覆盖，新旧可对照
- AI 帮你挖因子时，能直接读全量特征口径，不会瞎猜

## 五、文本 → 特征：六步管道

```
① ingest      已有 sources.yaml 驱动，只加 doc_id/content_hash
② normalize   去 HTML、繁简、压缩空白、跨源去重（content_hash 归并 dup_group）
③ link        实体链接：别名词典 + code 精确 + 全称 + 歧义消解 → doc_entity
④ extract     事件抽取（规则 + LLM 双通道）+ 情绪打分 + 主题分类 → ev_event
⑤ aggregate   doc → (entity, trade_date) 日频聚合 → 中间表
⑥ feature     注册 + 落值 + 质量门禁 → feat_value
```

每一步必须满足：**幂等（同输入重跑结果不变）+ 带 `version`（升级不覆盖）**。

第 ③ 步是整个方案的核心工作量，也是你现在最大的漏洞。

## 六、现有管道的三个必修问题（不修，知识库建在沙上）

### 问题 1 · 用「今天的股票名」匹配「历史的文本」

**位置**：`backend/app/datahub/cleaners/core.py:127-143` `load_name_map()`

```python
for sym, nm in db.execute(select(Stock.symbol, Stock.name)).all():
    ...
    pairs.append((clean, sym))
```

只读 `stocks.name`（**当前**简称）。三个后果：

1. **改名公司历史文本全漏**：`stocks` 只有当前名，2020 年的文本里用的是当时的名，匹配不上
2. **只覆盖简称**：工商全称、曾用名、子公司名、英文名、港股/美股关联主体，全部漏掉
3. **无词边界**：「中国建筑」会命中「中国建筑集团」「中国建筑装饰」等非上市主体，而黑名单只挡了 30 个泛词

**修法**：建 `ent_entity` 表，`aliases_json` 存全量别名（含历史名 + 全称 + 常见简称 + 拼音），匹配时按别名长度降序 + 前后字符边界校验 + 输出 `match_type` 和 `confidence`。别名表可以从 `stocks`、公告正文、交易所名录三处生成。

### 问题 2 · 情绪是累计值，不是当日值

**位置**：`backend/app/datahub/cleaners/core.py:146-168` `upsert_stock_sentiment()`

```python
row.bull_score = int(row.bull_score or 0) + int(bull)     # ← 累加
row.net_sentiment = round((row.bull_score - row.bear_score) / ...)  # ← 用累计值算
```

`net_sentiment` 实际是「自入库以来累计多空比」，日频因子失去时间局部性，5 日变化率、20 日 z-score 全部算不出来。而且重复跑靠 `processed_ids.json` 文件状态防重（第 172 行），文件一丢数据就翻倍。

**修法**：改为「当日值覆盖 + 长表存文档级分数」，日频聚合由 `feat_value` 按 `trade_date_applicable` 重算，天然幂等。

### 问题 3 · 没有 `available_at`，公告类数据必然前视

现有表只有 `date`。公告/新闻一律按自然日归档。盘后发布的公告被算进当天截面，就是前视。

`news_stock_daily` 全部 6,768 行都无法判断「这条信号当时到底可不可用」。这批历史数据在修完 PIT 之前，**不能用于任何回测**。

## 七、第一批 24 个特征（不依赖 LLM 就能算一半）

分五组。括号内是计算口径，`T` = `trade_date_applicable`。

### A. 关注度（Attention）

| feature_id | 口径 | 备注 |
|---|---|---|
| `text.mention_cnt_1d` | `count(doc)` | 当日提及篇数 |

## 八、这件事直接决定 GP 挖掘的上限

你已经有 `factor_gp.py`。GP（遗传规划）的本质是在**原子特征池**上做符号回归搜索：

```
候选因子 = f(x1, x2, ..., xn)     n = 原子特征数量
```

你现在喂给 GP 的是 14 个量价 + 基本面因子。GP 无论怎么交叉变异，产出都是「动量 × 换手」「EP / 波动率」这类组合——**搜索空间已经见底**，边际收益递减是必然的。

加 24 个文本/事件特征后，搜索空间从 14 个原子扩到 38 个，组合数增长**两个数量级**，而且新增的这批与量价因子**低相关**——这才是 GP 能挖出新东西的前提。

同时也带来新风险：**过拟合**。38 个原子特征跑 GP，不做严格样本外，挖出来的"年化 60%"因子 100% 是噪声。所以 `ds_snapshot`（训练集快照）不是锦上添花，是必需品：每次挖掘必须绑定一个 `snapshot_id`，换特征/换区间就换快照，结果才可复现、可比对。

| **S4**（1 周） | 首批 10 个特征落 `feat_value` + IC 验证 + 质量门禁 | 特征覆盖率、IC/ICIR、PIT 泄漏检查全绿 | 待做 |

**S1.5 顶到 S2 前面，是 S1 跑完才发现的**：33 个交易日的数据量，即使 S2 把覆盖率做到 50%，也验证不出任何东西。先把时间跨度补够，再谈覆盖率。

S2 是成败关卡。如果实体链接做不好，后面全是白干——所以 S2 结束必须先看「覆盖率」这一个指标，不达标就返工，不要往下走。

## 十、技术选型：明确不引什么

| 需求 | 方案 | 明确否决 |
|---|---|---|
| 文档存储 | Parquet（按日期分区）+ SQLite 元数据 | ❌ MongoDB（单机多一套运维） |
| 全文检索 | **SQLite FTS5**（已建 `doc_fts`） | ❌ Elasticsearch（1.4GB 语料用不上） |
| 结构化分析 | DuckDB（已有） | — |
| 向量检索 | v1 不上；要上就用 DuckDB VSS 扩展 | ❌ Milvus / Qdrant（单机无必要） |
| 关系图谱 | `ent_relation` 表 + 递归 SQL | ❌ Neo4j（关系规模 < 10 万条） |
| 事件抽取 | 规则 + LLM 双通道，`extractor` 字段区分 | ❌ 纯 LLM（成本高、不可审计） |
| 特征服务 | DuckDB + SQL，长表 | ❌ Feast（Python 单体服务，杀鸡用牛刀） |

原则：**单机、零新增常驻服务、全部 SQL 可查**。你现在的架构（FastAPI + SQLite + DuckDB + Python daemon）已经够用，这套设计不让它变复杂。

## 十一、验收标准（量化，可打勾）

| 指标 | 门槛 |
|---|---|
| 截面覆盖率（有至少 1 条文本信号的股票占比） | ≥ 50% |
| 实体链接准确率（抽 200 篇人工核） | ≥ 90% |
| 事件抽取准确率（抽 200 条） | ≥ 85% |
| 跨源文档去重率 | 去重后 ≤ 原量 70% |
| PIT 泄漏检查 | 100% 特征通过（`available_at ≤ trade_date 15:00`） |
| 首批特征有效数（\|IC\| > 0.02 且 ICIR > 0.3） | ≥ 3 个 |
| 全链路重跑幂等 | 同输入重跑，`feat_value` 行数与值完全一致 |

最后一条最容易被忽略，但最重要：**不幂等的管道，跑三次就会出现三套数字，然后你就不知道该信哪个了。**

## 十二、待你拍板的三件事

1. **语料边界**：只做 A 股（公告 + 新闻 + 公众号），还是要把互动易/上证 e 互动、研报、雪球也纳进来？后两类噪声大但独家信息多，建议第二批再说。
2. **LLM 预算**：事件抽取用 LLM 的话，按日均 3,000 篇、每篇 1 次调用估，DeepSeek 约 ¥1–2/天。是否接受？还是先只跑「公告」这一类（日均 300 篇，成本降 90%）。
3. **落地位置**：这套表建在现有 `quant_dev.db`（同库多表），还是另开 `knowledge.db`（物理隔离）？我倾向**同库**——跨库 join 在 SQLite 里很痛苦，而且你已有 `pipeline_runs` 这套监控可以复用。
