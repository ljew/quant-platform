1. 定位与设计原则

QUANT·DESK 是单用户、本机运行的 A 股量化投研平台。目标用户是个人投资者本人：每天打开网站第一眼看到「今日观点」，其余事情——数据更新、因子挖掘、信号生成、组合跟踪、复盘归因——全部由系统自动完成。

五条设计原则：
  • 本地优先：全部数据与计算在本机，无外传；无账号体系，打开即用。
  • 数据自给：行情、成分、基本面自动日更，断供自动补抓，PIT（point-in-time）成分快照按月刷新。
  • 自动闭环：挖因子 → 评级入库 → 每日信号 → 模拟盘镜像 → 每周复盘 → 迭代建议，全链路无人值守。
  • 安全边界：自动化只到「因子层」；信号策略的升降档由系统出建议、人来确认（或显式授权后执行）。平台不含实盘交易（2026-09-30 决策，实盘路由已摘除）。
  • 一切幂等：所有定时任务可重跑、可补跑，重启不产生重复副作用（DB 级判重）。

3. 数据层：Bronze → Silver → Gold

数据管道遵循经典分层，每层职责单一：

层内容形态
Bronze原始采集：日 K、指数、成分、基本面，原样落盘Parquet 分区（data/raw/**）
Silver清洗校验：复权对齐、缺失处理、质检报告SQLite 表 + 质检 JSON
Gold应用就绪：因子截面、信号明细、组合镜像SQLite + DuckDB 镜像
  • 每日 19:00（交易日）：data_scheduler 自动 ETL 日更；检测到断供会自动补抓缺口；每月自动刷新指数成分 PIT 快照（回测用「≤ 调仓日的最新快照」作合法股票池，杜绝未来函数）。
  • 双库分工：SQLite 是业务事实库（事务、写入）；DuckDB 是分析镜像（聚合、回测扫描快）。健康检查里有「DuckDB 同步一致性」一项保证两者行数一致。
  • 交易日历：app/core/trading_calendar.py，akshare 在线拉取并缓存 data/trading_calendar.json，内置 2020-2026 节假日表兜底。所有调度器据此判断「今天跑不跑」。

4. 研究流水线（每日 19:00）

orchestrator 把每日研究编排成 8 个步骤，每步有事件日志，重活走 subprocess 隔离 + 硬超时：

data → quality → research → signal → backtest → attribution → risk(闸门) → publish
数据就绪   数据质检    研究计算    信号生成    回测校验     归因分析      风险闸门      结果发布
  • 交易日 19:00 自动触发；错过则下次启动时补跑（幂等）。
  • risk 是闸门：质检不过会阻断后续步骤并留事件记录，避免脏数据污染信号。
  • 与 19:00 的 ETL 并存：流水线用的数据若未到当日，会以最近可用交易日为准，两个调度器均幂等。

5. 信号引擎 xq

5.1 策略与质量分级

9 个信号策略，每个有质量档 strong / neutral / weak（xq/strategies.py: STRATEGY_QUALITY），定档依据本平台 240 日独立复测（T+1 开盘建仓、T+10 收盘卖出、超额 vs 全市场等权），并随每周复盘滚动校准：

档位含义当前策略（2026-09-30 复盘后）
strong长期与近期均为正超额high_tight_flag（高紧旗形）
neutral正超额但稳定性待观察chan_buy（缠论买点）
weak近 90 日超额为负，仅观察不建仓rps_breakout、dual_param、private_placement、limit_up_shakeout、ma_volume、turtle_trade、uptrend_limit_down

5.2 动作判定（judge）

对每只连续命中的股票，结合连续天数（streak）、共振数、最优策略档位（best_tier）与均线位置，给出当日动作：

动作触发条件（简化）
BUY_STRONG连续达标 且 best_tier ≠ weak（weak 档再多连续也只给 WATCH）
WATCH确认中 / 策略偏弱 / 跌破 MA10 短线走弱 / 多日共振仅参考
REDUCE跌破 MA20 趋势转弱，建议减仓
EXIT信号消失，保留观察
NEW今日首次出现，持续性待确认

组合镜像严格 T+1 开盘成交 防前视：今日 BUY_STRONG → 次一交易日开盘买入。

6. 因子体系与 GP（已熔断）

  • 因子注册表（factor_registry）：只有 enabled 的因子进入每日生产计算。
  • 检验口径：截面 Rank IC、分层收益、换手与容量，截面抽样约每月一次。
  • GP 挖掘（已熔断 2026-10-08）（factor_gp.py）：遗传规划在表达式空间进化。当前默认关闭，gp_search() 直接返回 disabled，恢复需设 QUANT_GP_ENABLED=1（不推荐直接恢复）。
    熔断原因：实测 37 个输出全是 roc(c,6) 一类单变量变体、无任何交互项；fitness 与种群选择在同一全样本内完成（结构性过拟合）；26/37 为负 IC，其中 7 个曾被误判「可用」并进入注册表。复活前置：M3-1 样本外框架 + M3-2 IC 周频化 + 估值因子 PIT 修复。详见 docs/REBUILD-2026-10.md §1.3。
  • 评级四档：优秀 / 可用 / 弱 / 无效——决定落库后的去向（见下节闭环）。
  • LLM 释义：对挖掘出的表达式生成人类可读解释，供应商在页面配置，改完即时生效。

7. 自动研究闭环

2026-09-30 上线（services/auto_research.py），把「研究」这件事全自动化：

每个交易日 20:47（ETL 与流水线之后）
  GP 挖矿（16 个体 × 5 代）
    → 精英评级
      ├─ 优秀 → 自动 enabled 进生产注册表（次日即参与每日计算）
      ├─ 可用 → 登记为 candidate，等人看
      └─ 弱/无效 → 不留存，只进运行记录
每周六 10:15
  自动复盘：90 日滚动归因（T+1/T+5/T+10 胜率与超额）
    + 模拟盘组合镜像 + 因子盘点
    → HTML 报告（data/reports/）+ 邮件推送
    → 走弱策略生成「建议降级」清单（不自动执行）
安全边界（有意设计）：自动化的范围只到因子层——自动挖、自动评级、自动启停。信号策略的降级只出建议，由人确认后改档（避免一次异常行情误杀长期有效的策略，如 rps_breakout 240 日 +2.45% 但 90 日 −1.21% 的情形）。
幂等防重：调度器做 DB 级判重（当日/当周已跑则跳过），launchd 重启不会重复触发。
配置：data/auto_research.json（开关、时间、种群规模、是否自动启用优秀因子、是否邮件），页面「数据中心 → 自动研究」可视化维护。

8. 监控、健康度与节假日静默

  • 健康度引擎（health_engine.py）：规则存库（health_rules 表，页面可增删改阈值/启停），三层评分（采集 35% / 处理 35% / 应用 30%）合成百分制健康分。
  • 节假日静默（holiday_mode.py）：非交易日自动把「数据停更」类检查（新鲜度/管道最近运行/质检时效）的失败降级为 ok + muted，不进告警；真实故障（DuckDB 不一致、数据量异常）照常报警。模式：auto（默认，非交易日自动）/ on / off，监控页横幅可切换。
  • 系统监控页：健康分、告警、管道运行记录、服务存活、30 秒自动刷新，可一键手动触发管道。
